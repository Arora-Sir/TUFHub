# TUFHub Architecture

This is the mental model a newcomer (human or AI) needs before changing code here. It covers the structure and the non-obvious decisions behind it. Read the source for the line-by-line details. Anything a comment can say better at the point it matters belongs in that comment, and this file covers the shape of the system.

## What this is

A Chrome extension (Manifest V3) that watches takeuforward.org for an accepted problem submission and commits the solution code straight to a GitHub repository, automatically, with a generated README per problem and a solved-problems index at the repo root.

## The two-world split, and why it constrains everything

Manifest V3 content scripts run in one of two JS realms on the same page:

- **MAIN world** (`interceptor.js`): shares the page's own `window`, so it can monkey-patch `fetch`/`XMLHttpRequest` to observe TUF's own API traffic, and read `window.monaco` directly for editor content. It has no access to `chrome.*` extension APIs.
- **ISOLATED world** (`content.js`): has `chrome.*` APIs (storage, runtime messaging) but a separate JS environment from the page: it cannot see variables or call functions defined in MAIN world, even though both are injected into the same tab.

They talk to each other only through `CustomEvent` instances dispatched on `window` (`TUFHUB_USER_SUBMIT_CLICKED`, `TUFHUB_SUBMISSION_SNAPSHOT`, `TUFHUB_ACCEPTED_SUBMISSION`, `TUFHUB_DIAG`). There is no shared module between them. This is why some logic (extracting the active tab's name, reading the editor's code) exists as near-duplicate implementations in both files rather than one shared function. MAIN world cannot `import` from ISOLATED world's modules at runtime, and the reverse direction is not worth the indirection for logic that is cheap to keep in sync by hand. Routing is the exception in the other direction. `router.js`'s `resolveHierarchy()` and `syncJob.js`'s `buildSyncJob()` are pure (they read only their payload, never the page), so `content.js` bundles them to build a job and the background worker bundles the same code to convert queue items written by older versions.

## Two detection channels, on purpose

A verdict can be observed two ways. `interceptor.js` sees TUF's own API response carrying the verdict (the primary, fast path), or `content.js` polls the DOM for accepted-verdict text as a backup. Both exist because the primary path is inherently fragile against a moving target. TUF's API endpoints and response shapes are not a contract this project controls, and a new site revamp can silently start returning a shape the interceptor does not recognize, or introduce an endpoint that is not in the allowlist yet (see `interceptor.js`'s endpoint allowlist and the `UNMATCHED_ENDPOINT` diagnostic events it logs when something new shows up unrecognized). The DOM-text backup is slower but reads only rendered text, which is far less likely to change shape invisibly. Both channels carry the same submit token for a submission, and `content.js` lets only the first one to arrive through.

Every submission is frozen once, at submit intent, and nothing after that reads page state. `content.js` sees the Submit click (or Ctrl+Enter) in the capture phase, before TUF's own handler runs, creates the submit token, and records the page-side context for it: topic hints from the sidebar (`captureTopicHints()`) and a degraded fallback snapshot for when the interceptor is unavailable. The interceptor, told about the click through `TUFHUB_USER_SUBMIT_CLICKED`, takes the real snapshot in the same instant: the Monaco code and language id, the editor tab's label and count, the URL, slug, title, difficulty, description, and syllabus topic. When the outgoing `POST /judge/submit` request carries the code, the request body overrides the editor read, since it is exactly what the judge runs. When no click was detected (an icon-only button, an unrecognized shortcut), the snapshot is taken at that request instead. The POST response only records the submission id and never re-reads the editor, because the user can switch editor tabs during that round trip, and a slow judge (SQL polling in particular) leaves even more time for that before the verdict lands.

Verdicts are matched back to their snapshot by that submission id whenever the response carries it, so a history row for a different submission (another tab's older accepted code, for example) is ignored rather than synced, and two back-to-back submissions from different editor tabs each keep their own code. TUF itself stops polling a submission's verdict as soon as the user submits again (confirmed live), so an older submission whose id has gone unpolled for a few seconds is polled by the interceptor with the page's own `check-submit` request shape. Its headers stay in memory and go to that same endpoint. The interceptor shares its snapshot with `content.js` through `TUFHUB_SUBMISSION_SNAPSHOT`, so the DOM watcher syncs exactly the same data as the primary channel. The DOM watcher is also bound to the submitted problem (it stops if the tab navigates away) and only counts a verdict after the page has shown no accepted verdict at some point since the click, so the previous submission's result panel cannot trigger it.

## Routing: `router.js`

`classifyPath()` recognizes any `/practice/<subject>/<slug>` URL generically. Adding a future TUF subject (an HLD sheet, for example) needs no code change, just a folder name it will pick up from the URL's own subject segment. Anything that is not a syncable problem page (`/practice-test/`, `/learning/`, `/prep-hub/`) is recognized and explicitly skipped rather than falling through to a default category.

`resolveHierarchy()` resolves topic and subtopic through the same priority order for every subject: TUF's own syllabus API first, then a subject-specific fallback chain only when that data has not been observed yet.

- **The syllabus API is the primary source, not the sidebar.** `interceptor.js` passively observes the `/api/v2/syllabus/track?type=source&key=<subject>` response the page already fetches on load and flattens it into a slug-to-topic lookup covering the whole track (`buildSyllabusMap`). This replaced sidebar-DOM scraping as the primary DSA signal after a TUF site revamp removed the syllabus sidebar from the problem page entirely: the old `SyllabusSidebarContent` selector matches nothing there now, so it was silently returning empty on every DSA sync until this fix. The syllabus API also gives SQL topics their real, fine-grained taxonomy names (such as "Querying Essentials") instead of the five coarse hardcoded buckets (Joins, Aggregation, Subqueries, Data-Engineering, Basics) the old fallback still uses.
- **DSA** falls back to the sidebar's expanded accordion trail captured at submit intent, then the URL's `category` query param, then a title/slug keyword guesser, only when the syllabus map has no entry for the submission's slug. The keyword guesser is a last resort. Several of its checks (`bst`, `ll`, `dp`, `bfs`, `dfs`) are short abbreviations, and bare substring matching on them misfiled problems whose slugs merely contained those letters (such as "sub-BST-rings" or "a-LL-three-characters"). `hasToken`/`hasExactToken` in `util.js` require a word boundary before matching, closing that class of false positive. `rootReadme.js`'s independent topic-display guesser had the identical bug and got the identical fix.
- **SQL** (and any other generic subject) falls back to the URL's `category` query param, then the same keyword-bucket guesser, under the same condition.

`resolveHierarchy()` is pure. It reads its payload (the frozen URL, title, syllabus topic, and the topic hints captured at submit intent) and never touches `window` or `document`. The DOM is read exactly once, by `captureTopicHints()` on the page being submitted, and each hint set carries the slug it was read on, so a mismatched set is ignored. A route can be computed away from the submission in both time and place, for example when a verdict lands minutes later or when the background worker converts a legacy queue item. Routing from the live DOM in that situation reads whichever page is on screen, which is how an open SQL tab's sidebar sent a DSA sync to `DSA/Aggregation-and-Grouping/` (BUG-011). The syllabus topic reaches both detection channels through the interceptor's snapshot. A syllabus response that resolves after the click fills pending snapshots by their own frozen track and slug, never by the page's current URL.

The GitHub folder slug itself always comes from the URL's own last path segment, never from the page title. Deriving slugs from problem titles failed on SQL sheets where titles carry problem numbers (such as "47. Profitable Customers in 2021"), which mistakenly zero-padded leading numbers into folder names.

## Sync pipeline

A sync writes through GitHub's Git Data API directly (blob -> tree -> commit -> ref PATCH), not the simpler contents API, so a submission with multiple files (a multi-tab problem's several solutions plus its README) lands as one atomic commit instead of several.

`content.js` never commits. It builds one frozen job (`buildSyncJob()` in `syncJob.js`: destination folder, file name, code, and the problem README) and hands it to the background worker with a `SYNC_JOB` message. The worker (`syncQueue.js`) persists the job to `tufhub_queue` before replying, then runs the whole pipeline for it (repo stats check, root README, commit, stats update, code hash) inside the one serialized write lock (`enqueueGitHubWrite` in `writeQueue.js`) that reconciles and deletes also use. Two writers (two open tabs, a manual Sync click landing mid-submission, a delete's own follow-up reconcile) therefore never race each other's ref updates, and the root README is always built from stats that include every commit that landed before it. A newer submission of the same file supersedes an older one still waiting in the queue, and an identical one is acknowledged as a duplicate.

Retries live only in the worker. A ref-update conflict (GitHub's "not a fast forward") is first retried with backoff inside `commitTreeEntries`. If it persists, the job stays queued and is retried on a backoff schedule, using an in-process timer for short delays and a `chrome.alarms` alarm as the wake-up backstop, since alarms cannot fire sooner than 30 seconds and MV3 can stop the worker between retries. Offline failures do not spend the retry budget, but a job expires after 24 hours rather than committing stale code much later. Because the worker has no page attached, a retry cannot read whichever TUF tab happens to be open. Progress and results go to the tab that submitted the job (`TUFHUB_SYNC_STATUS`). That tab shows them while it still displays the same problem, or when the same document handed the job off, which covers moving to the next problem inside TUF's single-page app while a sync runs. A reloaded page or a different tab never handed the job off, so it does not show an earlier page's result. The badge and Sync Health record the outcome in every case.

Every GitHub read that must be current goes through `ghGet()` in `uploader.js` with `cache: 'no-cache'`. GitHub answers with `Cache-Control: private, max-age=60`, so a plain `fetch` can return a branch ref up to a minute old, and every retry of a back-to-back push would then build on the same outdated parent and fail as "not a fast forward". That stale ref pushed quick second submissions into the retry queue. Revalidating costs nothing against the rate limit, since GitHub does not count 304 responses. A commit whose tree matches the branch head is skipped rather than created empty, and code hashes are keyed by full file path (`folderPath/fileName`), so a copy in the wrong folder can never make the same code look already synced for the right one.

## Stats and reconcile: local cache, GitHub as source of truth

`stats.problems` in `chrome.storage.local` is a cache, not the record of truth: every field in it except title/difficulty/topic is meant to be correctable from GitHub's own state. `reconcileRepoFromTree` (the popup's "Sync" button, and automatically after every delete) walks the live repo tree and rebuilds this cache from what is actually there, including re-fetching each problem's real last-commit date from GitHub rather than trusting whatever `updatedAt` is already cached locally. This makes the cache self-healing against local corruption rather than merely correct at write time, avoiding historical bugs where local reconcile functions unconditionally stamped today's date onto all problems.

Duplicate detection groups repo folders by slug (the last path segment). A problem that used to sync to one folder and now syncs to a different one (after a routing fix, for example) leaves its old copy behind as an orphan, surfaced to the user as a duplicate rather than silently losing one copy.

## Milestone nudge: a monotonic watermark, not a reactive listener

The popup's Support section includes a small banner marking every 10 problems solved, read once from `stats.solved` when the popup opens rather than from a live `chrome.storage.onChanged` subscription: a milestone crossed by a background sync while the popup is already open simply surfaces the next time it opens, trading a session of delay for zero risk of the banner appearing mid-click and shifting the layout under the user's cursor.

`tufhub_milestone_last_shown` is a watermark rather than a boolean flag. It stores the highest milestone already shown, moves forward and never back, and is written at show time rather than on dismiss. `stats.solved` can decrease after a duplicate-folder cleanup or a Sync reconciliation that finds fewer live problems than the local cache expected. A drop like that can make a future milestone look not yet crossed, but it cannot re-arm one that already fired, because the watermark never moves backwards. The close control is a plain dismiss with no separate opt-out flag. A single click in an earlier version disabled the feature forever, and clearing extension storage by hand was the only way to undo it.

## File map

- `src/scripts/tuf/interceptor.js`: MAIN world. Network interception, submission snapshots at submit intent (including the outgoing request body), submission-id matching of verdicts (primary channel), syllabus map caching.
- `src/scripts/tuf/content.js`: ISOLATED world. Submit-intent tokens and topic hints, the DOM-text backup detection channel, building one frozen job per accepted submission, handing it to the background worker, and rendering the status toasts the worker sends back.
- `src/scripts/tuf/router.js`: payload to folder-path resolution. `resolveHierarchy()` is pure. `captureTopicHints()` is the only DOM reader and runs once at submit intent.
- `src/scripts/tuf/syncJob.js`: `buildSyncJob()`, which freezes route, file name, code, and README into a job, including the guard that keeps a description-less sync from overwriting an existing problem README.
- `src/scripts/tuf/syncQueue.js`: background worker only. The durable job queue: persistence, dedupe and supersede, the commit pipeline, retry scheduling, badge, and status messages to the originating tab.
- `src/scripts/tuf/writeQueue.js`: background worker only. `enqueueGitHubWrite`, the single FIFO lock every repository mutation runs through.
- `src/scripts/tuf/readme.js`: per-problem README generation (HTML to Markdown).
- `src/scripts/tuf/rootReadme.js`: repo-root solved-problems index generation.
- `src/scripts/tuf/stats.js`: local stats cache, the two reconcile functions, path-keyed code-change hashing for dedup.
- `src/scripts/tuf/uploader.js`: the actual GitHub Git Data API calls (`commitTreeEntries`, `deleteFiles`, `uploadToGitHub`) and the revalidating `ghGet()` read.
- `src/scripts/background.js`: service worker. Message routing between popup/content script and the sync queue, the retry alarm, reconcile and delete handlers, install/update re-injection.
- `src/scripts/popup.js` / `src/popup.html`: the toolbar popup UI: auth, stats, Sync button, duplicate-folder panel, Sync Health diagnostics, and the Support section with its milestone nudge banner.
